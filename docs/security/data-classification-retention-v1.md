# US-0003 data classification and retention inventory — v1

Status: W0 documentation-contract draft; not an approved privacy, legal, or production retention policy.
Owner: Security (classification and access-control inventory); each data steward listed below owns operational lifecycle within its bounded context. Product owner and counsel must settle the decisions in “NOT DECIDED” before production use.
Scope: US-0003-A/B, traced to TC-US-0003-A/B. Inputs reviewed: ADR-0001 (accepted modular monolith/application-service and event boundaries), ADR-0002 (accepted canonical ledger and rebuildable projections), approved W0-1 architecture contract (`docs/architecture.md`), `database/schema.sql`, `database/README.md`, `docs/backlog/b-004-refinement.md`, `test-cases.md`, `AGENTS.md`, identity/privacy/audit/backup/observability smoke contracts, and the roadmap's local synthetic implementation evidence. No existing `docs/security/` or privacy inventory was present at review time.

## Classification and handling vocabulary

- Restricted: authentication material, account-linked financial activity, raw provider/import content, private reports/exports, identity data, and security audit evidence. Access is limited to the data subject and explicitly authorized service/operator roles for a documented purpose; portfolio reads/writes must be authorized server-side at each application boundary and scoped to the relevant portfolio/account. No broad support or provider access is implied.
- Confidential: portfolio/account configuration and derived financial information that can identify or materially describe a user's finances. Same tenant/portfolio scoping applies; grants are least-privilege and revocable.
- Internal: operational metadata and synthetic fixtures. Operational metadata may still contain sensitive identifiers or reveal security posture, and must not be treated as public.
- Public: only deliberately published reference data (for example, currency definitions or public market facts) after separate source/use review. User-linked records do not become public because `privacy_scope` or a share mechanism exists.

All access controls below are requirements, not proof that database row-level security exists: `database/README.md` says RLS is future work. API/application authorization must therefore be checked server-side on every request/job, including object access, export, report download, and background processing. A UI-hidden field is not an access control. Service identities should receive only the context/data needed for their task; operator access must be time-bounded, purpose-bound, and audited. Provider adapters and AI/addons do not get direct ledger writes (ADR-0002 / AGENTS.md).

## Inventory

### User identity and authentication

- Classification: Restricted.
- Representative fields: `app_user.id`, `email`, `display_name`, `status`, `locale`, `timezone`, `default_currency_code`, `tax_residency_country`, `deleted_at`; `auth_identity.provider`, `subject`, `email`, `metadata`; preferences; session `token_hash`, expiry/revocation timestamps; TOTP ciphertext/IV/tag; OIDC state/code hashes and redirect URI. Never store or expose raw session tokens, OIDC state/code, TOTP seed, password, or recovery code in logs, exports, fixtures, or audit snapshots.
- Authorized access: user may access own identity/preferences; Identity application services and narrowly scoped auth workers may process required fields. Support/operator access only for an approved incident/purpose and with audit. Never use an email or client-supplied user ID as proof of identity.
- Masking / redaction: omit email and auth metadata by default in logs/traces; mask email when operationally necessary; expose stable opaque IDs instead. Hash opaque session/state/code values; encrypt TOTP secret material. Exports include only the requesting user's entitled identity fields, excluding credential material and token hashes unless a separately approved portability requirement says otherwise.
- Audit requirement: login, identity lifecycle, factor enrollment/revoke, session revoke, recovery, export, and privileged access record actor, action, entity, timestamp, `trace_id`, and `correlation_id`; audit payloads contain no raw credentials or codes.
- Retention / deletion owner: Identity & Access owner owns account lifecycle and identity/auth records; Security owns review of access evidence. Keep records only for a documented operational/security purpose and approved schedule. User deletion is currently a soft-delete/revoke lifecycle: set deleted state/time, revoke sessions/factors/grants and prevent re-authentication; do not interpret this as immediate erasure of every linked record.
- Backup / restore treatment: identity/auth records are included only in protected encrypted backups needed for recovery; restore must preserve revoked/deleted state and must not reactivate sessions, factors, or grants. Credential values are not made recoverable by a database restore; vault/key recovery is separate.

### Portfolio and account metadata

- Classification: Confidential; increase to Restricted where metadata includes provider identifiers, account hints, or sensitive free text.
- Representative fields: portfolio owner/name/description/status/privacy scope/reporting currency; membership role and revocation; `financial_account` name/type/institution/currency/dates/metadata; provider-account external identifier/name/last four IBAN hint; connection/scopes/consent metadata and sync status/errors; instrument identifiers (ticker/ISIN/CUSIP) and user labels.
- Authorized access: portfolio members only, with permissions enforced by server-side role and portfolio/account scope at every read/write boundary. Owner/editor changes are limited to documented capabilities; viewers/accountants/advisors receive only their granted read scope. Integration workers can access only the connection/account being processed. Cross-portfolio and outsider access is denied.
- Masking / redaction: do not log account names, external IDs, IBAN fragments, free-text descriptions, consent payloads, or provider metadata. Where support needs identification, use internal IDs and mask account hints. Sanitize provider error messages before persistence/rendering.
- Audit requirement: membership/role/grant/revoke, privacy-scope changes, account/connection/consent changes, and privileged reads are auditable with actor/entity/trace/correlation. Do not copy complete before/after secret or provider payload values into audit.
- Retention / deletion owner: Portfolio owner owns portfolio/account configuration; Integrations owner owns provider-connection and sync metadata; Identity owns grant revocation. Archive/revoke on user deletion or disconnect according to the approved lifecycle; no period is currently approved. A shared portfolio's other members' rights and records must be evaluated separately from deletion of one user.
- Backup / restore treatment: protect within encrypted database backups; restore must preserve membership revocations, connection/consent revocation and archive state. Do not restore credentials from ordinary DB backup; validate references against the vault and keep revoked references revoked.

### Canonical ledger activity

- Classification: Restricted (financial activity and account-linked positions/balances).
- Representative fields: `ledger_transaction` portfolio/account/provider links, activity type/subtype/state, dates, description, external ID/hash, source/payload references, paired transaction, metadata, creator and void/correction timestamps; `ledger_entry` amount, quantity, price, currency, reporting amount, FX, fee, tax, notes and metadata; tax lots/disposals; linked income events. Fields in flexible JSON/description/notes can contain sensitive content and inherit Restricted classification.
- Authorized access: server-authorized portfolio/account members for permitted reads; only Ledger application commands can create/correct/void canonical activity. Provider/import/AI/agent/read-model paths may not directly mutate canonical ledger tables. Re-check actor, active membership, role, target portfolio/account, and requested operation in the application boundary; never rely on UI controls.
- Masking / redaction: do not put activity descriptions, amounts, identifiers, or provider payload content in routine logs/traces. Use entity IDs, counts, coarse status, and approved redacted reason codes. Avoid full ledger rows in errors, audit before/after, and test output.
- Audit requirement: record actor, action, entity, trace/correlation and relevant correction/VOID reason; retain original activities and entries as audit history. ADR-0002 and AGENTS.md prohibit physical deletion of ledger activity; financial projections are rebuildable and not the canonical source.
- Retention / deletion owner: Ledger owner owns canonical transaction/entry and correction lifecycle; Privacy/Identity owner coordinates data-subject requests; product owner and counsel decide any lawful retention/erasure treatment. Current contract says no physical deletion of ledger history and does not define a retention duration. Account/user soft-delete must not cascade-delete canonical activity or erase correction history.
- Backup / restore treatment: include canonical ledger and required references in encrypted database backups for recovery; restore must retain VOID/correction/audit linkage and be separately verified. A user deletion request does not itself authorize purging ledger rows from a backup. Any backup expiry/purge and restore-after-deletion handling remains a policy decision; a restore must reapply deletion/revocation state before serving traffic.

### Raw provider payloads and imports

- Classification: Restricted. Treat raw payload, uploaded statements, webhook bodies, CSV/XLSX/PDF, raw rows, normalized/resolved rows, and provider identifiers as potentially containing full account and transaction data.
- Representative fields: `raw_provider_payload.payload_json` / object-storage object, checksum, endpoint, content type, captured time and `retention_until`; `import_file.filename`, storage key, checksum and size; `import_row_review.raw_row`, normalized/resolved values and reviewer; webhook event IDs/signature status; sync cursors/checkpoints/diagnostics and reconciliation evidence.
- Authorized access: the owner and specifically scoped portfolio members/reviewers for the related import/connection; Integration worker only for the active job; object-storage reads require server-side ownership/scope checks, not knowledge of an object key. No provider receives data back except the minimum request needed for its authorized protocol. Raw evidence is not a ledger-write capability.
- Masking / redaction: never log or trace raw bodies, file contents, rows, access tokens, account numbers, transaction descriptions or full cursors. Store object references and checksums in logs where needed. Do not paste raw samples into tests; use synthetic data only. Restrict download URLs and set safe, private response headers.
- Audit requirement: upload, provider capture, read/download, review/correction, commit/undo, and purge are auditable with actor/service, entity, trace/correlation and outcome; audit records refer to payload IDs/checksums, not content.
- Retention / deletion owner: Integrations owner owns raw provider payload lifecycle; Import owner owns uploaded file/session/row lifecycle; Privacy owner coordinates access/deletion requests. Schema has optional `retention_until`, but no approved default or period. Retain no longer than the documented processing/reconciliation purpose once a schedule is approved; deletion of source evidence must not silently delete canonical ledger history.
- Backup / restore treatment: database rows and object-storage objects are both sensitive and must be backed up encrypted with integrity checks and matched references. Restore testing must verify a synthetic raw payload can be read as in TC-US-0107-C, while preserving object ownership boundaries. Expired/deleted data can reappear from backups unless backup expiration and restore-time deletion replay are defined; this is unresolved, not an erasure guarantee.

### Reports and exports

- Classification: Restricted when user/portfolio-derived; a report artifact is a portable copy of its included source data.
- Representative fields: `report_run` owner/portfolio, type/period/filters/status/object key/expiry/error; generated JSON/CSV/XLSX/PDF; privacy export bundle containing user, owned portfolios, ledger, raw references, reports and grants per TC-US-0206-A. Export may include direct identifiers and financial details.
- Authorized access: requesting authenticated user may export only self-owned/authorized scope; report generation/download workers receive only scoped inputs and output destination. Re-check ownership/role and expiry on every status/download request. Do not provide a public object URL or permit cross-tenant artifact-key access.
- Masking / redaction: do not log report contents, filters that may contain PII, object keys usable as credentials, or export response bodies. Export must exclude password/secret material, raw session credentials, TOTP secrets, OAuth tokens, and unrelated users' private data/grants.
- Audit requirement: export request, generation, download, failure, deletion/expiry and share must record actor, entity, purpose/action, trace/correlation and timestamp without embedding the artifact contents.
- Retention / deletion owner: Reports owner owns report artifact lifecycle; Privacy owner owns user export request semantics; artifact owner must delete expired or revoked artifacts when policy is approved. `artifact_expires_at` is a schema field, not an approved duration. User export is a copy; generating it does not itself delete source records.
- Backup / restore treatment: generated files in object storage are sensitive; include only if recovery requirements justify it and protect with encryption/checksum. On restore, reapply artifact expiry/deletion and sharing revocations before access. Backup copies may retain an artifact past active-object deletion until the approved backup lifecycle ends.

### Credentials and secret references

- Classification: Restricted (highest sensitivity class in this inventory).
- Representative fields: `credential_secret_ref.vault_path`, secret kind, key version and lifecycle timestamps; encrypted TOTP material; secret/config references; OAuth/API key/client secret/session token/recovery material. The reference itself can disclose provider/user association and is sensitive. `app_setting.is_secret` is not evidence that the value is safely stored.
- Authorized access: only the secret-management boundary and the specific service identity authorized for the named operation; no routine human, general application, report, AI/addon, provider adapter, or database-reader access. Enforce narrow scope and explicit, audited access; revocation/rotation must be effective server-side. Never put secret values in Git, fixtures, screenshots, logs, traces, audit payloads, exports, or task notes.
- Masking / redaction: never render or log raw values; redact secret/token/password/code/private-key patterns before logs or errors. Show only non-sensitive status and opaque reference ID. Store tokens as hashes where verification-only (sessions/OIDC/AI grants) or encrypted via approved vault/KMS mechanism where later retrieval is needed.
- Audit requirement: access, creation, rotation, recovery, failed lookup and revoke require actor/service, secret-reference entity, purpose/action, trace/correlation and timestamp; never log value, hash intended as bearer material, ciphertext, nonce or recovery code.
- Retention / deletion owner: Security/secrets owner owns vault policy and access review; Identity owns auth-factor lifecycle; Integrations owns provider credential-reference lifecycle. Revoke/rotate when account/connection is deleted, user is deleted, compromise is suspected, or purpose ends. Exact secret version retention and destruction schedule is NOT DECIDED.
- Backup / restore treatment: do not put plaintext secrets in DB backups. Ciphertext or references may be restored only if the encryption key/vault remains separately controlled and the reference is still active. Restore must not undo revocation or resurrect obsolete credentials; recovery of keys/vault material is a separately authorized and tested process.

### Audit records

- Classification: Restricted security/accountability metadata; may reveal user identity, financial entities, access patterns or incident details.
- Representative fields: `audit_log.user_id`, actor type/ID, action, entity type/ID, before/after JSON, correlation/trace IDs, IP hash and timestamp; incident/audit event evidence. Before/after JSON is untrusted for sensitivity and inherits the highest classification of included values.
- Authorized access: audit service writes through the controlled application boundary; users may view only the audit events permitted by their account/portfolio scope; Security/Operations may query for an approved security or incident purpose with least privilege. No direct database broad access is implied.
- Masking / redaction: omit raw tokens, full IP addresses, secrets, financial values, free-text descriptions and payloads. Keep only minimal action/entity context; IP hash remains sensitive and must not be treated as anonymous without assessment.
- Audit requirement: audit access to audit records where feasible; records require actor, entity, timestamp, `trace_id` and `correlation_id` for relevant request/job; access-denial and export/delete events must retain safe evidence. Do not recursively copy sensitive audit fields into another log.
- Retention / deletion owner: Security owns audit policy; Operations operates storage/rotation; context owner confirms event meaning. No retention duration or immutability/WORM guarantee is approved here. User soft-delete may null/retain actor reference according to schema and must not silently destroy necessary security evidence; legal requirements are unresolved.
- Backup / restore treatment: audit is included in protected backups needed for investigation/recovery. Restore preserves event order/context and deletion/retention state; backup expiration and any legal hold must be separately applied. No claim of tamper-proof audit storage is made.

### Logs and traces

- Classification: Internal by default; Restricted whenever a trace/log includes user/account/provider identifiers, authentication metadata, IP hash, exception payload, or financial context.
- Representative fields: request/job/service/release IDs; `trace_id`, `correlation_id`, job ID; status/error code, route, timing, deployment/incident details; exception text, span attributes and baggage. Test-cases TC-US-0106-A/B/C require traceability and redaction, specifically excluding tokens, account numbers and transaction descriptions.
- Authorized access: service/operations personnel and scoped observability services for operations/security purposes; restrict query/export by environment, service and role. User-facing support sees sanitized summaries only. Do not propagate authorization headers, raw request bodies or full provider payloads to telemetry.
- Masking / redaction: allowlist safe fields; redact tokens/secrets/API keys/account numbers/transaction descriptions and direct identifiers; scrub exception and URL/query parameters; do not put sensitive values in span names, baggage, metric labels, test output or CI artifacts. Use synthetic test sentinels to verify absence.
- Audit requirement: privileged access/export of logs/traces and security investigations should be traceable; application events preserve trace/correlation linkage without duplicating sensitive payloads. Operational logs are not substitutes for domain audit.
- Retention / deletion owner: Operations owns log/trace storage and purge controls; Security approves redaction and access; service owners prevent sensitive emission. No log/trace retention period is approved in the reviewed contract.
- Backup / restore treatment: logs/traces are not canonical ledger recovery inputs; backup only where incident/recovery policy requires, encrypted and access-limited. Restore must honor configured expiration and deletion; no retention or deletion behavior is claimed by this inventory.

### Synthetic fixtures and test evidence

- Classification: Internal, explicitly synthetic and non-identifying; promote classification if any fixture contains real or plausibly identifying data.
- Representative fields: `SEC-001`, `ENV-001`, sample users/emails at reserved `example.test`, synthetic account/transaction/provider payloads, trace/correlation IDs, test outputs and CI artifacts.
- Authorized access: repository contributors and CI identities with repository access; no real provider/bank/model credentials, customer data, production tokens, private keys, or copied production records. CI artifacts are access-controlled and ephemeral only if the CI policy actually guarantees that.
- Masking / redaction: synthetic-only; secret and PII sentinel scans; never echo credentials/codes in failing assertions or snapshots. Use clearly synthetic names/IDs; avoid real account patterns or reachable endpoints.
- Audit requirement: fixture changes and test/CI execution are covered by repository history and CI run identity; never use fixture values as production credentials. Attach trace/correlation context to test commands and preserve only safe test summaries.
- Retention / deletion owner: each fixture/test owner maintains the fixture; repository/CI owner controls artifact lifecycle. Remove accidental sensitive data immediately through the incident/secrets process (including history/artifact cleanup); the normal fixture policy does not justify retaining actual PII.
- Backup / restore treatment: synthetic fixtures may be included in repository/CI backups; verify no credentials or real personal data enter those backups. Synthetic test evidence must not be mistaken for production privacy/compliance evidence.

## Lifecycle boundaries and evidence limits

- User deletion currently means application-level soft delete and revocation behavior described by US-0206/TC-US-0206: user status/deleted timestamp, session/factor/OIDC-state invalidation and grant revoke; own portfolios are archived; canonical ledger history is not physically deleted. Export covers owned portfolios/grants and fixed ledger/raw/report sections. This is local synthetic implementation evidence, not a universal erasure or legal-compliance conclusion.
- A backup is a separate copy and is not erased by active-record deletion. Restore can reintroduce deleted/revoked material unless the restore procedure reapplies a deletion/revocation ledger before exposure. Existing US-0107 contract asserts encrypted artifacts, checksums, retention metadata and synthetic raw/report restore, but it does not define a production retention schedule or deletion replay policy.
- Legal hold, if authorized by counsel, suspends only the specific deletion/expiry actions identified in a recorded hold, for the minimum scope/duration, with owner, authority, review/end date and access restrictions. The system has no evidenced legal-hold mechanism in the reviewed schema/contract; this sentence is a proposed boundary, not an implemented capability. Do not place a hold or extend retention based on this draft alone.
- No class is assigned a jurisdiction-specific period. `raw_provider_payload.retention_until` and `report_run.artifact_expires_at` are fields, not policy values. The roadmap reports a local synthetic backup configuration with `retention_days: 30`; that is environment-specific implementation evidence only and is not approval of a data-class, legal, or production retention period.
- This inventory documents intended controls. It does not establish production RLS, complete redaction coverage, automated purge, backup deletion propagation, encryption-key lifecycle, legal hold, full export completeness, or regulatory compliance.

## NOT DECIDED — minimum owner/legal decisions before production policy

1. Product owner + counsel: applicable jurisdictions, data-subject deletion/retention obligations, statutory/accounting/security retention duties, and any conflict with canonical ledger non-deletion; define the minimal lawful retention exceptions and evidence basis.
2. Data owners (Identity, Portfolio, Ledger, Integrations/Imports, Reports, Security, Operations) + counsel: approve an explicit retention trigger, duration, deletion/anonymization method, and verification evidence for every inventory class, including raw payloads, imports, reports/exports, audit, logs/traces, identity and backups.
3. Privacy owner + product owner: define what user export includes/excludes, treatment of shared portfolios and other members' data, deletion of object-store artifacts, and how a soft-deleted user's references are minimized without breaking ledger integrity.
4. Operations + Security: define backup schedule/expiry, encryption/key custody, restore access, deletion/revocation replay before service, and handling of a backup restored after an erasure request; decide whether a backup's configured 30-day local value has any intended production analogue (no assumption made here).
5. Counsel + named records owner: approve legal-hold authority, scope, start/end/review workflow, notice/access restrictions, and how a hold interacts with active deletion and backup expiry; confirm whether any technical legal-hold capability is required before production.
6. Security + Operations: approve observability field allowlists, retention, access/egress boundaries, and redaction verification; confirm whether IP hashes, provider identifiers, trace baggage, and diagnostic metadata are personal/sensitive under the chosen jurisdictions.
7. Security/secrets owner + Operations: approve vault/KMS, backup/reference, rotation, revocation, key destruction and recovery schedules; specify which encrypted secret references can be restored and how revoked references remain unusable.

- TC-US-0003-B: every class names a lifecycle owner and describes backup/restore and deletion/soft-delete boundaries; unknown periods/legal rules and legal-hold mechanism are explicitly NOT DECIDED rather than invented.
- Tests: `tests/smoke/data-classification-retention-contract.test.mjs` is the documentation-contract check; it does not test runtime authorization, purge, restore, or compliance.
- Gate: draft only. Independent review found one stale next-gate reference requiring correction. After this correction, the next gate is a new independent QA review. This task does not close US-0003 acceptance or production privacy/compliance and authorizes no provider, UI, or financial implementation.
